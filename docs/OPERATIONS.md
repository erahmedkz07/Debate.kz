# Эксплуатация Debate.kz

Как сайт бережёт данные, следит за собой и сколько выдерживает. Все команды выполняются в папке `backend`
и читают настройки из `backend/.env`.

| Команда | Что делает | Как часто |
|---|---|---|
| `npm run backup` | копия базы и загруженных файлов | каждый день |
| `npm run backup:verify` | доказывает, что копия восстанавливается | раз в неделю |
| `npm run monitor` | проверяет сайт каждую минуту, пишет админам в Telegram | постоянно (служба) |
| `npm run load-test` | нагрузочный тест на копии данных | перед запуском и после крупных изменений |

## 1. Бэкап

`npm run backup` делает два файла в `backend/backups/auto`:

- `debatekz-ГГГГ-ММ-ДД_ЧЧММ.dump` — база (pg_dump, сжатый формат). Сразу после создания читается через
  `pg_restore --list`: битая копия считается ошибкой.
- `files-ГГГГ-ММ-ДД_ЧЧММ.tar.gz` — загруженные файлы: обложки, логотипы, аватары (`uploads`) и чеки оплаты (`private`).

Старые копии прореживаются: хранятся последние 7 дней, 4 воскресенья и 6 первых чисел месяца (полгода истории
примерно в 17 копиях). Файлы, сделанные вручную (например, `backups/*.dump` перед миграциями), не трогаются.

Если бэкап не удался, админы, привязавшие Telegram, получают сообщение.

**Вторая копия вне сервера обязательна:** копия на том же диске не спасёт, если сломается диск или сервер. Укажите
`BACKUP_COPY_DIR` — папку на другом диске или синхронизируемую с облаком (Google Drive, Яндекс Диск, rclone-mount).
Каждая новая копия будет класться и туда.

### Проверка восстановления

`npm run backup:verify` берёт последнюю копию, восстанавливает её в отдельную временную базу `<имя>_restorecheck`,
сравнивает число строк в 11 главных таблицах с живой базой, проверяет архив файлов и удаляет временную базу.
Живая база только читается. Бэкап, который никто ни разу не восстанавливал, — это надежда, а не бэкап.

### Восстановление после сбоя (вручную)

```bash
# 1. остановить API, чтобы никто не писал в базу
# 2. пустая база и восстановление в неё
createdb -U postgres debatekz_new
pg_restore --no-owner --no-privileges -d "postgresql://…/debatekz_new" backups/auto/debatekz-2026-10-30_0300.dump
# 3. файлы — в STORAGE_DIR (или в backend/ на этом компьютере)
tar -xzf backups/auto/files-2026-10-30_0300.tar.gz -C "$STORAGE_DIR"
# 4. DATABASE_URL в .env → debatekz_new, запустить API, проверить сайт
```

## 2. Мониторинг

`npm run monitor` раз в минуту запрашивает `/api/health` (этот адрес проверяет и API, и базу).

- Две неудачи подряд — админам в Telegram «сайт недоступен» и причина.
- Сайт снова отвечает — «сайт снова работает (не работал N мин)».
- Раз в день: если самой свежей копии больше 26 часов, приходит «нет свежего бэкапа».

Состояние хранится в `logs/monitor-state.json`, поэтому можно запускать и как постоянную службу, и планировщиком
каждые несколько минут (`npm run monitor -- --once`).

Важно: монитор, запущенный на том же сервере, не заметит, что упал весь сервер. Для этого нужен внешний сервис
(UptimeRobot, Better Stack — бесплатно), который проверяет `https://<домен>/api/health` снаружи.

### Журнал ошибок

Каждая ошибка сервера (ответ 500) и каждое падение страницы у посетителя (страница сама сообщает о нём через
`POST /api/client-errors`, не больше 5 за загрузку) записываются в `logs/errors.log`: одна строка JSON на ошибку,
файл сменяется при 5 МБ. Без cookies, тел запросов и параметров адреса. Одинаковая ошибка приходит админам в
Telegram не чаще раза в 10 минут.

```bash
tail -n 20 logs/errors.log
```

## 3. Где и как это запускается

### Сейчас: этот компьютер (Windows)

Пока сайт работает на ноутбуке, расписание ставит Планировщик заданий:

```powershell
$b = "C:\Users\Acer\Downloads\Debate.kz\backend"
schtasks /Create /TN "DebateKz Backup" /SC DAILY /ST 03:00 /TR "cmd /c cd /d $b && npm run backup >> logs\backup.log 2>&1"
schtasks /Create /TN "DebateKz Backup Verify" /SC WEEKLY /D SUN /ST 04:30 /TR "cmd /c cd /d $b && npm run backup:verify >> logs\backup.log 2>&1"
schtasks /Create /TN "DebateKz Monitor" /SC MINUTE /MO 5 /TR "cmd /c cd /d $b && npm run monitor -- --once"
```

Задание сработает, только если ноутбук включён. Пропущенный бэкап монитор заметит и сообщит.

### После переезда на сервер (Ubuntu)

На сервере всё уже настроено в [`deploy/`](../deploy/README.md): `deploy/cron` каждую ночь запускает `backup.sh`,
а каждые 5 минут — `healthcheck.sh` (тревога в `ALERT_CHAT_ID`). Дублировать их не нужно. Из этих скриптов там
пригодятся:

```bash
cd /opt/debatekz/backend
# раз в неделю: восстановится ли копия (понимает и серверные копии db-*.dump)
BACKUP_DIR=/var/backups/debatekz node --env-file=/etc/debatekz/api.env scripts/backup-verify.mjs
```

Проверке восстановления нужно право создавать базы (`ALTER ROLE … CREATEDB`), иначе запускайте её от `postgres`.
Журнал ошибок (`logs/errors.log` в `STORAGE_DIR`) на сервере работает сам, без настройки.

## 4. Настройки (backend/.env)

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `BACKUP_DIR` | `backend/backups/auto` | куда класть копии |
| `BACKUP_COPY_DIR` | — | вторая копия: другой диск или облачная папка |
| `STORAGE_DIR` | `backend` | где лежат `uploads`, `private`, `logs` (в продакшене обязательно) |
| `ALERT_CHAT_IDS` (или `ALERT_CHAT_ID`) | админы с привязанным Telegram | кому слать тревоги (id через запятую) |
| `MONITOR_URL` | `http://127.0.0.1:$PORT/api/health` | что проверять |
| `PG_BIN` | `C:/Program Files/PostgreSQL/<версия>/bin` или PATH | где pg_dump и pg_restore |

Тревоги отправляет тот же бот, что и уведомления сайта (`TELEGRAM_BOT_TOKEN`). Без токена они только печатаются.

## 5. Нагрузочный тест

`npm run load-test` (около полутора минут; `-- --quick` — 20 секунд):

1. восстанавливает последнюю копию в отдельную базу `<имя>_load`;
2. запускает API на порту 4500 в production-режиме, с его лимитами и кэшем;
3. «посетители» открывают то, что открывают во время турнира: список, турнир, таблицу, сетку, страницу спикера,
   рейтинг — без пауз, ступенями по 10, 50, 100 и 200;
4. удаляет копию.

Результат на ноутбуке (Acer Nitro 5; API, база и сам тест на одном процессоре), данные ZHABAYEV CUP 2026
(31 команда, 55 дебатов), 30.10.2026:

| Посетителей | Запросов/с | p50 | p95 | Ошибок |
|---|---|---|---|---|
| 10 | 1287 | 6 мс | 14 мс | 0 |
| 50 | 1303 | 29 мс | 56 мс | 0 |
| 100 | 1377 | 48 мс | 111 мс | 0 |
| 200 | 1312 | 61 мс | 504 мс | 0 |

До кэша публичных страниц (`src/lib/shortCache.ts`) было около 200 запросов/с, а страница спикера при
200 посетителях отвечала 3,7 с.

Как это читать: открытая страница турнира обновляется раз в 30 секунд, плюс клики человека — в среднем
0,1–0,2 запроса в секунду. 1300 запросов/с — это порядка нескольких тысяч человек, одновременно смотрящих
турниры. Узкое место — один процесс Node (одно ядро). Несколько процессов сразу запускать нельзя: каждый поднимет
своего Telegram-бота, а два бота с одним токеном мешают друг другу (сначала нужно вынести бота в отдельный процесс).
Цифры с реального сервера будут другими — тест нужно повторить там.
